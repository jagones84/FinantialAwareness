## Goal

Apply the smallest safe patch to the in-app AI agent so it handles the stability weight `w` (`bonusStdWeight`) consistently with the real simulation logic, without changing unrelated app behavior.

## Scope

- Expose `bonusStdWeight` explicitly in the agent prompt as an allowed override for simulation and optimization requests.
- Remove misleading prompt wording that can encourage proxy reasoning through `P3` when the app already supports direct `w` overrides.
- Align agent-generated stability reporting with the actual app formula and scaling used by the simulation logic.
- Add focused automated tests around the changed behavior.

## Non-Goals

- Do not change the optimization search space beyond the current `P1..P4` parameter search.
- Do not redesign the objective function.
- Do not refactor unrelated agent, UI, persistence, or simulation flows.
- Do not change chart, profile, or navigation behavior.

## Current Problems

### 1. Prompt / executor mismatch

`AgentToolExecutor` accepts `bonusStdWeight`, but `PromptConstructor` does not clearly advertise it in the tool contract shown to the model. This makes the model more likely to invent indirect reasoning paths.

### 2. Misleading stability wording

The prompts currently describe the stability index in a way that does not match the calculation shown in the simulation logic. This can produce incorrect explanations in chat and reports.

### 3. Incorrect agent-side stability report scaling

The optimization analysis generated by the agent reports stability using `stdDev / bonusStdWeight`, while the app logic uses `stdDev / (bonusStdWeight / 100)`.

## Recommended Approach

Use a narrow compatibility patch:

1. Keep the executor contract unchanged except for clarifying prompt support.
2. Update prompt text so the model knows it can directly vary `bonusStdWeight`.
3. Update agent prompt/report wording to match the actual formulas used by `SimulationLogic`.
4. Add focused JVM tests for:
   - prompt exposure of `bonusStdWeight`
   - stability formula/report consistency where feasible without broad integration setup

This is the lowest-risk option because it avoids touching simulation math and avoids expanding optimization behavior beyond what the app already guarantees.

## Data / Logic Impact

- No persistence schema changes.
- No model shape changes for saved profiles.
- No UI layout changes required.
- No change to simulation outputs except correcting agent explanations/reporting.

## Testing Strategy

- Add or update small JVM tests around agent prompt text and stability calculations/reporting helpers.
- Run targeted unit tests first.
- Run diagnostics on edited Kotlin files.
- Only run broader verification if the change footprint requires it.

## Acceptance Criteria

- The agent prompt explicitly lists `bonusStdWeight` as an allowed override.
- Agent/report text no longer implies `P3` is a substitute for `w`.
- Agent stability reporting matches the same scaling used in `SimulationLogic`.
- Existing app behavior outside the agent/report path remains unchanged.
